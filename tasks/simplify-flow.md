# Nope: two-step setup and two-stage correction

This spec supersedes the setup flow in prototype.md. Preserve the existing app, saved data, and Vexo kit. The user explicitly requests a simpler, fun mobile flow, assumes band 58 connected, keeps the pastel cards, and assigns detection to their friend.

## User experience
1. Home: keep reference-inspired white surface, huge black headline, six pastel two-column cards, black bottom nav. Heading `What do you want to end?`. One natural-language description input. Cards: Doom-scroll, Nail biting, Vaping, Smoking, Porn, Snacks, each filling editable example text. No device connection step. Small `Band 58 · Ready` status from config; do not claim a hardware connection was verified.
2. Penalty: direct from description, NO clarification route, NO natural-language response-plan editor, NO separate review form. Heading `Make it count.`. Show model-selected category in a compact editable category chip/select and the user's description. User can correct the category inline. Six supported categories: Doom-scroll (`scrolling`), Nail biting (`nail_biting`), Vaping (`vaping`), Smoking (`smoking`), Porn (`porn`), Snacks (`snacking`). The former `drinking` ID is unsupported and is never remapped to `porn`. Unknown/uncertain text goes to this same screen with `Choose the closest habit`, no forced confident match.
3. Two fixed stage cards on penalty screen: cyan `1. A friendly nudge` / `As soon as it happens`; yellow `2. Put your money on it` / `Still happening after 1 minute?`. Three large selectable dollar chips: $1, $5, $10. Default $5 is a clearly visible proposed choice. One `Start my rule · $5` action saves and activates, then shows the rule. The button itself is the review/confirmation of the displayed two-stage terms. No extra setup wizard.
4. Small payment status below amount: `Stripe test mode` and card status/connect-test-card action if test secret configured. If no secret configured: `Demo penalty · no real money` and simple help instruction. Do not bury main action in setup notices. Do not pretend payment succeeded if demo/unconfigured/failed.
5. Saved rule detail: category headline, original description, chosen amount, same two-stage compact summary, pause toggle, edit, delete, `Try it`. Preview displays in-app notification then next button `Still doing it` displays clearly simulated penalty; `I stopped` ends. Preview NEVER calls Stripe. Keep Activity (preview vs detector labels), help, and navigation, simplify their copy. All visible branding Nope.
6. The band/detection is assumed as context, not implemented. Friend's events drive the same two-stage UI through SSE. Backend owns any test charge, not browser timers. Actual mobile background push remains unimplemented; be honest in help/status, keep UI otherwise focused on user's rule.

## Shared API (exact)
GET /api/config extends existing response with:
`behaviors: [{id,label,ongoingLabel}], penaltyAmounts:[1,5,10], graceSeconds:60, decisionModel:string|null, stripe:{mode:'demo'|'test',connected:boolean,cardLabel:string|null,message?:string}`.
Ids fixed: scrolling, nail_biting, vaping, smoking, porn, snacking. Labels Doom-scroll, Nail biting, Vaping, Smoking, Porn, Snacks. The former `drinking` ID is unsupported and is never remapped to `porn`. ongoingLabel e.g. `Still smoking`.
POST /api/classify {description:string} => {mode:'gemini'|'demo',behaviorId:string|null,confidence:number|null}. Use current official Gemini Decision API if available, documented exact request schema. Result classifies the intended target habit, NOT evidence that behavior occurred. Include unsupported/none sentinel internally; map it to null. No followup question. Demo fallback keyword-based, truthful, only for absent key, not silent on API failure. Reject malformed model output; unknown/low score (<0.55 if score available) returns null.
POST /api/rules and PATCH /api/rules/:id accept new compact payload `{description,behaviorId,penaltyAmount}` (enabled patch remains supported). Validate catalog and allowed amounts. Build a version 2 rule with `schemaVersion:2, description, behaviorId, penaltyAmount, currency:'usd', graceSeconds:60` and retain id/enabled/createdAt/title plus legacy fields behavior/trigger/responsePlan/steps for compatibility. Exactly two steps: notification at0 and commitment at1minute. Existing legacy rules remain readable and unmodified; they NEVER cause a Stripe charge until explicitly edited/converted. UI may show legacy as `Update this rule` and edit into the new penalty screen.
GET /api/rules remains {rules}.
POST /api/rules/:id/stop with {} => {ok:true}, serialized with detector event processing; cancels the active episode for the user's I stopped / False alarm action. Frontend must await success for detector sessions. Local previews never call it. Hide Reset preview in detector mode.
POST /api/payments/setup => {url}; browser redirects to Stripe TEST hosted setup checkout.
POST /api/payments/complete {sessionId:string} verifies session server-side and returns payment status. Callback main URL has `?stripe_setup_session={CHECKOUT_SESSION_ID}`; cancel URL `?stripe_setup=cancelled`. Persist draft in sessionStorage before redirect, restore after. Process callback, then clear query via history.replaceState. Never trust the query alone as success.
GET /api/payments/status => payment status shape above.

## Stripe module exact interface
`export class StripePayments` constructor `{secretKey, dataDirectory, appOrigin, fetchImpl=fetch}`.
- `status()` async => `{mode:'demo'|'test',connected:boolean,cardLabel:string|null,message?:string}`. Absent key = demo. Only sk_test_ (and optionally documented restricted test key prefix) accepted; never use live keys. Invalid/live config must remain unable to call Stripe and explain test-key requirement without exposing values.
- `createSetup()` async => `{url}`. Use official hosted Checkout setup mode, own Customer, fixed appOrigin callback URLs. Persist setup ownership and customer/payment method locally in ignored .data; no secret persistence. appOrigin fixed to actual localhost server address, never arbitrary client-supplied URL.
- `completeSetup(sessionId)` async => status. Verify own created session, mode/setup complete, customer match; fetch SetupIntent and card details via Stripe. Do not accept another session/account just because query says complete.
- `charge({amountDollars,idempotencyKey})` async => `{status:'demo'|'succeeded'|'not_connected'|'failed',paymentId?:string,message?:string}`. Fixed usd, validate amounts [1,5,10], off_session confirmed PaymentIntent using saved customer/method and idempotency header. Return actionable safe error for authentication required/declined, NEVER mark failed/pending as succeeded. No test key => demo (not success). No card => not_connected.
Native fetch/form encoding; bounded timeouts, safe errors; no extra SDK dependency necessary. Module tests mock Stripe; do not call live endpoints without user-configured keys.

## Correction engine and detector contract
Existing POST /api/events with bandNumber=58, ruleId,eventId,phase started|continued|stopped remains. Still validate band, enabled rule, event id dedup. Emit named SSE `detection`; payload extends with optional `correction:{stage:1|2,status:'preview'|'demo'|'succeeded'|'not_connected'|'failed',amountDollars?:number,message?:string}`.
On started: persist new episode, record SERVER receipt start time, stage1 preview notification. No charge.
On continued: after at least60sec by SERVER clock, version2 rule and active episode, apply chosen penalty at most once for this episode. Below60sec remainsstage1. Do not rely on supplied occurredAt to accelerate payment. On stopped: end episode, no further charge for it. No started=>no charge. Paused/legacy rule=>no charge.
Serialize episode operations and persist idempotency key before charge; repeat events/restarts must not create duplicate penalties. Same Stripe idempotency key on retry after interrupted processing. Record outcome with episode; expose via SSE and event response. Use injected clock/payment service in tests for fast timing checks.
For demo mode, stage2 correction reports demo; no charge claim. Preview in browser is always local simulation regardless of configured card. Existing contact/call features can be removed from the new flow, and no messages/calls are ever sent.
